# Decision log

Append-only. Newest at the bottom. One entry per decision that would otherwise
be re-argued later.

Format:

```
## D-NNN — <title>
Date · Status: proposed | accepted | superseded by D-NNN | rejected
Context:     what forced a choice
Decision:    what we chose
Alternatives: what we rejected and why
Consequences: what this makes easy, and what it makes hard
```

A decision without alternatives and consequences is a note, not a decision.

## D-001 — Canonical context lives in the repo, not in Claude account memory
2026-08-16 · Status: accepted

**Context:** The project must survive a move to a different Claude session,
account, or machine with zero knowledge loss. Claude's conversation context is
not portable and is destroyed by `/clear` and lossy under compaction. The
account memory directory (`~/.claude/projects/<slug>/memory/`) is tied to one
account on one machine.

**Decision:** `docs/context/` in the git repo is the single source of truth —
`STATE.md` (current truth), `DECISIONS.md` (this file), `ENVIRONMENT.md`
(verified host facts), plus append-only `sessions/` and `audit/`. The account
memory directory holds **pointers only**, regenerated by
`.claude/skills/session-continuity/scripts/checkpoint.sh`.

**Alternatives:**
- *Account memory as primary* — rejected: not portable, which is the entire
  requirement.
- *Rely on transcript JSONL in `~/.claude/projects/`* — rejected: full fidelity
  but no signal; nobody can reconstruct intent from 100 KB of tool calls, and
  it is not versioned.
- *A single flat `SESSION_LOG.md`* (the common community pattern) — rejected:
  conflates current truth with history, so it grows until it stops being read.

**Consequences:** Makes handoff a `tar` and a `git clone`. Costs a hand-written
checkpoint at session boundaries — the curated layer needs judgment and cannot
be generated. Accepted deliberately.

## D-002 — Capture is automated by hooks; curation stays manual
2026-08-16 · Status: accepted

**Context:** "Save what we do after every output" cannot depend on the model
remembering to do it — the turns where it matters most are the ones where
context is already exhausted.

**Decision:** `.claude/hooks/` write the raw record deterministically every
turn: `record-prompt.sh` (UserPromptSubmit), `record-turn.sh` (Stop /
StopFailure), `audit-tool.sh` (PostToolUse / PostToolUseFailure),
`session-start.sh` (SessionStart rehydration), `guard-destructive.sh`
(PreToolUse safety gate). Curated files stay hand-written.

**Alternatives:**
- *Instruct the model in CLAUDE.md to write the log each turn* — rejected:
  fails exactly when needed.
- *Hook dumps whole turns into `instructions.md`* — rejected: unreadable within
  a day; the hook appends a one-line index row instead and the full text goes
  to `sessions/`.

**Consequences:** Capture is guaranteed. Cost is ~5 shell invocations per turn
and an append-only log that grows; it is small text and it is in git.

## D-003 — One canonical JSON log event for everything we emit
2026-08-16 · Status: accepted

**Context:** The user requires proper logging and audit with a proper format.
Ad-hoc per-service formats make correlation impossible and force a rewrite of
every emitter when a collector is eventually added.

**Decision:** One flat JSONL event shape — `ts`/`level`/`service`/`env`/`host`/
`event`/`outcome`/`msg` required, with a defined optional set — used by nginx
(`log_format json_main escape=json`), our scripts, and the Claude hooks. Full
spec in `.claude/rules/10-logging-audit.md`.

**Alternatives:**
- *Nginx default combined format* — rejected: not machine-parseable without a
  brittle regex, and it drops upstream timing.
- *Deploy Loki/OTel now* — rejected: on 2 vCPU the collector competes with the
  workload. The standard is chosen so a shipper can be added later as a
  collection change, not an emitter rewrite.

**Consequences:** Correlation by `request_id` works end to end. Costs discipline
at every new emitter. Nginx's `error_log` cannot emit JSON — accepted as the
one documented exception.

## D-004 — ARM64 constrains every image choice
2026-08-16 · Status: accepted

**Context:** Discovery found the host is `aarch64`, not x86_64. The original
planning brief did not state an architecture.

**Decision:** Every image gets an `arm64` manifest check before it enters a
compose file. No amd64-only image is deployed, with or without emulation.

**Alternatives:** *`qemu`/binfmt emulation* — rejected: on 2 vCPU the CPU cost
is not affordable, and it adds a failure mode that is hard to diagnose.

**Consequences:** Image selection is narrower, and Guacamole in particular needs
verification before Phase 7 is planned in detail. Better found now than at
deploy time.

## D-005 — Commit after every major action
2026-08-16 · Status: accepted

**Context:** On a single-node platform with no staging, the git commit is the
rollback point. Batching a session's work into one commit produces a rollback
point that covers six unrelated changes and therefore cannot be used.

**Decision:** Commit immediately after each major action — phase complete,
service added, behaviour-affecting config edited, decision recorded, rules or
hooks changed, or before starting anything risky. Config and its `DECISIONS.md`
entry go in the **same** commit. Trigger table in
`.claude/rules/30-secrets-git.md`.

**Alternatives:** *Commit at session end* — rejected, see above. *A commit hook
that auto-commits every turn* — rejected: produces meaningless messages, and a
rollback point is only useful if its message says what it restores.

**Consequences:** Fine-grained history and usable rollback. More commits.
`git push` still requires the user to ask — committing is automatic,
publishing is not.

## D-006 — Remote access is Kasm Workspaces CE, not Apache Guacamole
2026-08-16 · Status: accepted (user decision)

**Context:** User directive. Guacamole is adequate for basic browser SSH/RDP
but not for the intended personal-administration workflow — specifically
clipboard, file transfer, browser desktop, terminal quality, session
management, and MFA.

**Decision:** Kasm Workspaces Community Edition at `https://DOMAIN/webrdp/`,
path-based. Guacamole, guacd, and their PostgreSQL are removed from the plan.
Everything else in the plan is unchanged.

**Alternatives:** *Keep Guacamole* — rejected on UX. *Subdomain
`kasm.DOMAIN`* — rejected by the user; path-based routing is a first-class
requirement.

**Consequences:**
- Verified good: Kasm officially supports path-based proxying, and supports
  arm64 on Ubuntu 24.04. The architecture is viable.
- Requires Kasm-side zone config (`Proxy Path=/webrdp`, `Proxy Port=0`), not
  just an nginx block.
- **Resource cost is severe** — see D-007. This is the real risk, not the proxying.
- Kasm installs via its own script and owns its compose file, which sits
  awkwardly with "everything reproducible from git". The plan now requires
  documenting installer-owned vs our files.
- Kasm's agent likely needs the Docker socket to provision workspaces,
  introducing a trust boundary Guacamole did not have.
- The Guacamole fail2ban jail is removed; a Kasm jail is only added if
  investigation shows it can reliably extract a client IP from behind nginx.

## D-007 — Kasm's published requirements exceed this host; measurement gates the phase
2026-08-16 · Status: accepted

**Context:** Verified against current Kasm documentation:

| Item | Kasm's figure |
|---|---|
| Kasm services, host minimum | 2 cores / 4 GB / 50 GB SSD |
| Default workspace session | 2768 MB and **2 cores** |
| Swap | "strongly recommended for best stability of end user sessions" |

This host is 2 vCPU / 11 GiB / **0 swap**. Kasm's stated minimum is the entire
machine, and one default workspace wants both vCPUs — before nginx, Prometheus,
Grafana, Alertmanager, node_exporter, and the test site are counted. Rough
total ≈ 10.2 GB of 11 GiB, with the CPU budget already exceeded.

**Decision:** Do not set Kasm resource limits from estimates. Phase 7 is
sub-phased so that measurement (7c, 7g) gates progress, and if Kasm cannot
coexist with the monitoring stack, **stop and report the numbers** rather than
shipping something that OOMs on first real use. Concretely: reduce the
per-workspace allocation below Kasm's default, set memory *reservations* and
OOM scoring so a workspace is evicted before Prometheus, and cap concurrent
sessions at what the box can serve (realistically one).

**Alternatives:** *Accept Kasm's defaults* — rejected: guarantees the
denial-of-monitoring failure the user explicitly called out. *Drop monitoring
to make room* — rejected: defeats the purpose of the platform. *Resize the
VPS* — kept as an option to present if measurement says so.

**Consequences:** Phase 7 is slower and may not succeed. That is the correct
outcome if the hardware cannot support it — better found at 7c than in
production. Elevates O-005 (swap) from optional to a prerequisite.

## D-008 — 4 GiB swap file on `/`, swappiness 10
2026-08-16 · Status: accepted (user-authorised, implemented)

**Context:** The host had zero swap. Kasm's own documentation says swap is
"strongly recommended for best stability of end user sessions", and D-007
establishes that a workspace launch could otherwise OOM-kill Prometheus with no
grace period. User authorised a 4 GB swap file.

**Decision:** 4 GiB `/swapfile` on the root filesystem, `chmod 600`, persisted
in `/etc/fstab`, with `vm.swappiness=10` in `/etc/sysctl.d/99-swap.conf`.

**Alternatives:**
- *Swap on `/mnt/data`* — rejected. The data volume has far more room, but
  a swap file on a non-root mount depends on mount ordering at boot; if it
  silently fails to activate we lose the OOM protection exactly when Kasm needs
  it. 4 GiB is ~8 % of the 48 G root disk — cheap insurance for guaranteed
  activation.
- *Swap partition* — rejected: requires repartitioning a live cloud volume.
- *Default swappiness 60* — rejected. On 2 vCPU, routine paging is its own
  outage. Swap here is emergency headroom, so the kernel should be reluctant.

**Consequences:** A memory spike now degrades instead of killing. Does **not**
remove the need for per-container limits and reservations — 4 GiB of slow swap
is a grace period, not capacity. Root disk free space drops 48 G → ~38 G, which
sharpens O-011 (Docker data-root placement), since Kasm recommends 50 G storage.

Verified: `swapon --show` reports 4 G active, and a `swapoff -a && swapon -a`
cycle confirmed the fstab entry works. Not yet reboot-tested.

## D-009 — Manage the existing iptables ruleset; do NOT enable UFW
2026-08-16 · Status: proposed — needs user confirmation

**Context:** Discovery found `ufw` **inactive** despite its unit being enabled.
The live filter is plain iptables restored by `netfilter-persistent` from
`/etc/iptables/rules.v4`, shipped by Oracle's Ubuntu image. It already
implements default-deny via a trailing REJECT, and contains an Oracle
`InstanceServices` chain protecting the metadata endpoint.

**Decision (proposed):** Keep the existing iptables/netfilter-persistent
approach. Do not enable ufw.

**Alternatives:** *Enable ufw* — enabling it flushes and replaces the live
ruleset. The first casualty is the SSH ACCEPT rule we are connected through,
and Oracle's `InstanceServices` chain would also be lost. Doing it safely
requires the full lockout protocol and a console fallback. The original plan
assumed ufw; discovery says that assumption is expensive here.

**Consequences:** Firewall changes are hand-edited rules rather than `ufw allow`
— less friendly, but honest about what is actually running, and it keeps
Oracle's metadata protection intact. The Docker-bypasses-UFW trap in rule 20
still applies in full: Docker writes into the `DOCKER` chain regardless of
which frontend we use.

**Blocking sub-issue:** the live ruleset ACCEPTs 3389 from any source, and that
rule is **not** in `rules.v4`. Live and persisted state disagree, so the
firewall is currently not reproducible. Resolve as part of this decision.

## D-010 — Build the whole stack on the tailnet first; go public last
2026-08-16 · Status: accepted

**Context:** No domain has been bought yet, and one will not be for a while.
The obvious reading is that Phase 3 onward is blocked. It is not: this host has
a MagicDNS name (`onebox-prod.tailnet-example.ts.net`) and Tailscale issues **real,
publicly-trusted Let's Encrypt certificates** for `*.ts.net` via
`tailscale cert`.

**Decision:** Phases 1–10 run entirely on the tailnet, with nginx bound to
`tailscale0` and genuine TLS. Public launch becomes **Phase 11**: buy the
domain, open OCI 80/443, add a second nginx `server` block, issue a certbot
cert, enable HSTS. The tailnet listener is kept afterwards as the admin path.

**Alternatives:**
- *Wait for the domain* — rejected: stalls everything, including the two risks
  that can kill the plan (Kasm resources, arm64 workspace images). Finding
  those out after buying a domain is strictly worse.
- *Self-signed certificates for staging* — rejected: self-signed does not
  exercise real certificate validation, secure-cookie behaviour, or HSTS, so it
  is a weaker rehearsal for no saving over `tailscale cert`.
- *Public IP with a self-signed cert* — rejected: exposes the box during
  exactly the period when Kasm is least understood.

**Consequences:**
- The server stays completely unreachable from the internet through Phase 10.
- Kasm's subpath proxying, WebSockets, cookies, and resource behaviour are all
  proven under real TLS before any public exposure.
- No Let's Encrypt rate-limit consumption against the future domain.
- **Not** validated until Phase 11: public DNS, `www`→apex, certbot's `http-01`
  webroot flow, HSTS on the real origin, and the external uptime monitor. The
  §37 self-monitoring blind spot is unmitigated through Phase 10 — accepted,
  since nothing is in production.
- Prerequisite: HTTPS Certificates must be enabled once in the Tailscale admin
  console. Currently off (`tailscale status --json` → `CertDomains: null`).

## D-011 — Keep xrdp, avahi, and CUPS; the plan was wrong to list them for removal
2026-08-16 · Status: accepted

**Context:** `docs/PLAN.md` §19 listed `xrdp`, `rpcbind`, and `iperf3` for
removal as services with "no role here". Phase 1 discovery contradicted that for
xrdp, and the port audit surfaced `avahi-daemon` as a fourth candidate.

**Decision:** Disable `rpcbind` and `iperf3` only. **Keep `xrdp`, `avahi-daemon`,
and `cups`.**

**Evidence:**
- `xrdp` is in active use — the journal records a successful login for `prodadmin`
  from `100.100.160.47` (the phone on the tailnet) on 2026-08-15, and
  `loginctl` shows live sessions. The user confirmed they RDP in from their
  laptop and phone over Tailscale.
- `avahi-daemon` has `cups-browsed` as a reverse dependency, and `cups` is
  active. Disabling avahi would degrade printing in that RDP desktop session.

**Alternatives:** *Follow the plan and disable all four* — rejected: it would
have cut a working remote-access path and part of the desktop the user relies
on. The plan's reasoning ("no role") was an assumption, not an observation.

**Consequences:** Three non-loopback listeners remain that a minimal server
would not have (3389, 5353, and avahi's two ephemeral UDP ports). All are
REJECTed by the host firewall and unreachable via OCI, so the residual risk is
defence-in-depth only. Tracked as O-014.

**Lesson recorded deliberately:** a written plan is a hypothesis about the
system. Where Phase 1 observation contradicted it, the observation won.

### O-014 — Bind xrdp and avahi to the Tailscale interface? *(hardening, non-blocking)*
`xrdp` listens on `*:3389` and `avahi-daemon` on `0.0.0.0`. Both are firewall-
and NSG-blocked, so this is defence in depth rather than a live exposure.
Binding xrdp to `100.64.0.10` (`/etc/xrdp/xrdp.ini` → `address=`) would
close the gap, but restarting xrdp drops active RDP sessions — so it needs a
moment when the user is not connected. Decide before Phase 11, when the box
first becomes internet-facing.

## D-012 — Pin `backend-net`'s subnet so the node_exporter bind cannot drift
2026-08-16 · Status: accepted

*(Recorded late — this decision was made and referenced from
`host/systemd/node_exporter.service` during Phase 5, but the entry itself was
never written. Fixed 2026-08-16 to remove a dangling reference.)*

**Context:** Prometheus runs on `backend-net`, which is `internal: true` — no
egress, no default route. It therefore cannot reach `docker0`; it can only
reach **its own** network's gateway. node_exporter must bind to that gateway
for the scrape to work, and must never bind `0.0.0.0`.

That makes the gateway address load-bearing, and Docker assigns bridge subnets
dynamically — recreate the network and the address can change, silently
breaking the scrape.

**Decision:** create `backend-net` with an explicit subnet:

```bash
docker network create --internal --subnet 172.19.0.0/24 --gateway 172.19.0.1 backend-net
```

node_exporter binds `127.0.0.1:9100` and `172.19.0.1:9100`, and a narrow
firewall rule allows `172.19.0.0/24 -> 172.19.0.1:9100`.

**Alternatives:**
- *Let Docker choose, use `host.docker.internal`* — rejected: it resolves to the
  default bridge gateway, which an `internal` network cannot route to. Verified
  empirically before choosing.
- *Bind node_exporter to `0.0.0.0`* — rejected outright by rule 20.

**Consequences:** the scrape is stable across network recreation. The cost is
one more thing that must be recreated correctly — `docker network create` for
`backend-net` is no longer a bare command, and `host/README.md` records the
full form. Kasm's own networks are **not** pinned (they are installer-owned),
which is why the Kasm→host RDP rule in D-018 had to be written against
whatever subnet Kasm chose.


## D-013 — INCIDENT: Kasm's rclone plugin relocated the data volume and took the stack down
2026-08-16 · Status: contained; Kasm install **paused pending a decision**

**What happened.** During the Phase 7 Kasm install, the whole stack went down.
`docker ps` was empty, both custom networks were gone, and Docker reported
0 containers. No data was lost, but every service was offline for ~15 minutes.

**Root cause.** Kasm's installer installs a `rclone:latest` Docker plugin whose
config declares:

```
PropagatedMount: "/mnt"
```

It claims the **entire `/mnt` tree** as a shared propagated mount. Our data
volume is mounted at `/mnt/data`, so enabling the plugin caused Docker to
relocate `/dev/sdb1` to `/propagated-mount/data`. Docker's `data-root`
still pointed at `/mnt/data/docker` — which had silently become an empty
directory on the root filesystem — so Docker came back with a blank state.

The failure mode is nasty precisely because nothing errored: Docker started
"successfully" on an empty data-root.

**Recovery.** Stopped Docker, unmounted the leftover overlays, remounted
`/dev/sdb1` at `/mnt/data` from fstab (`mount --move` was refused —
"moving a mount residing under a shared mount is unsupported"), restarted
Docker, recreated both networks, and force-recreated every container. All data
intact: git repo, Prometheus TSDB, Grafana DB.

**Contained by** removing the `rclone` plugin, which we do not need (it exists
for cloud-storage mapping inside workspaces). Verified: a full Docker restart
now leaves the mount in place.

**Second bug this exposed**, fixed separately: nginx caches upstream DNS at
config load, so every backend that came back with a new IP produced a 502 until
a manual reload. On a platform whose premise is unattended recovery that is a
defect, not an inconvenience. Now uses Docker's resolver with a variable
`proxy_pass`; verified by forcing an IP change and by this very Docker restart,
after which nginx self-healed in under 8 seconds.

**Decision required before Phase 7 resumes** — see O-015.

**Lesson:** a third-party installer that runs as root can restructure the
host's mount table. The plan's Phase 7 gates covered resources and arm64; they
did not consider that the installer itself was a risk to the storage layout.

### O-015 — How should Kasm coexist with the data volume? *(blocking Phase 7)*

Three options:

1. **Install Kasm with `--skip-custom-rclone`, or remove the plugin after
   install.** Least invasive. Risk: an upgrade may reinstall it, and the
   failure recurs silently. Needs verification that Kasm functions without it —
   it should, since the plugin only provides cloud-storage mapping.
2. **Move the data volume off `/mnt` entirely** (e.g. `/srv/data`). Removes the
   collision permanently and is the robust answer. Cost: a migration touching
   Docker's `data-root`, fstab, every compose file, and the project path
   itself — this repo lives at `/mnt/data/projects`.
3. **Drop Kasm.** xrdp over Tailscale already provides the desktop; Kasm's
   value is browser access without a Tailscale client.

Recommendation: **option 2**, with option 1 as an interim if remote access is
wanted sooner. Option 2 is the only one that makes the failure impossible
rather than unlikely, and doing it now is far cheaper than after Kasm holds
state.

### O-016 — Kasm's sidecar plugin mounts the Docker socket *(security)*
`kasmweb/sidecar:1.2` mounts `/var/run/docker.sock`, `/proc`, `/run` and
`/var/log` from the host. That is the trust boundary flagged in T5/O-010,

## D-014 — Backups: local now, off-site outstanding; restore verified
2026-08-16 · Status: accepted (local), off-site pending a destination

**Context:** §25 requires local **and** off-site, and "a backup is not a backup
until a restore has been tested."

**Decision:** `scripts/backup.sh` nightly at 03:00 UTC via systemd timer
(`Persistent=true` so a powered-off box catches up). Dumps the Kasm DB with
`pg_dump` and Grafana with `sqlite3 .backup` — never a file copy of a live
database. Config archived; `.env` files archived **encrypted and separately**.
14 daily / 8 weekly retention.

Success writes a node_exporter textfile metric, which `BackupStale` watches.
The metric is written **only on full success**, so a partial failure ages it
and alerts rather than looking healthy. Verified flowing into Prometheus.

**Restore tested 2026-08-16 — PASSED.** `scripts/restore-test.sh` restores into
scratch and asserts *content*, not just exit codes: 2 users, 76 settings,
2 groups, sqlite `integrity_check: ok`, and critically that the zone
`proxy_path` still reads `/webrdp` — the setting git cannot protect.

**The restore test earned its keep on first run:** it failed. The encrypted
secrets archive would not decrypt. Cause was not the passphrase but file
permissions — the archive is 0600 root-owned and the test ran unprivileged.
The original diagnostic said "the passphrase does not match", which would send
someone restoring at 3am down entirely the wrong path. Fixed to distinguish
unreadable from undecryptable.

**Outstanding:** off-site copy. Local backups die with the VPS, which is the
scenario they exist for. Cheapest good answer here is a second Tailscale node
(`your-laptop`) via restic/borg — needs a destination decision from the user.

**Also outstanding:** the passphrase lives in `.backup-env` on this host. It
must be stored somewhere the VPS dying does not take with it, or the encrypted
secrets are unrecoverable in exactly the disaster they are for.

## D-015 — Kasm services had no memory limits; capped at the §22 budget
2026-08-16 · Status: accepted

**Context:** Phase 10 validation found every Kasm container running with
`Memory=0` — no limit, i.e. entitled to all 11.65 GiB. §22's whole resource
model assumed Kasm was capped at ~3.5 G; it was not. Kasm's generated compose
sets no limits, and we had not noticed because idle usage is modest (~866 MiB).

This mattered more than it looked: `oom_score_adj` decides *who* dies under
pressure, but only limits decide *whether* pressure happens at all. Without
them a single Kasm component could have driven the host into OOM, and the
protection would merely have chosen the victim.

**Decision:** `mem_limit` on all eight services, set from observed steady state
plus generous headroom: api 768M, manager 640M, agent 512M, guac 512M, db 512M,
share 256M, proxy 128M, redis 128M. **Total 3456M**, matching the §22 budget.

**Alternatives:** *Leave uncapped and rely on oom_score_adj* — rejected, see
above. *Cap tightly at observed usage* — rejected: workspace provisioning
spikes, and a limit that kills the agent mid-launch is worse than none.

**Consequences:** Host memory is now genuinely bounded. Applied to Kasm's
installer-generated compose, so it must be **re-applied after every upgrade** —
recorded in `kasm/INSTALLER-OWNED.md`. Two services (`db`, `kasm_redis`) use
unquoted `image:` lines and were missed on the first pass; worth knowing if
this is ever scripted again.

## D-016 — Kasm login fixed by patching an upstream inheritance bug
2026-08-16 · Status: accepted (workaround; remove when upstream fixes it)

**Context:** Phase 7 was blocked because every *successful* Kasm login returned
500. Invalid credentials returned 403 correctly, so the deployment looked
healthy until the password was right.

**Root cause**, established by disassembling the shipped `.pyc`: `PublicAPI`
extends `AdminApi`, but `hubspot_api_key` is only initialised in
`ClientApi.__init__` — a class not in that object's MRO — while
`_generate_auth_resp`, reachable from `PublicAPI.authenticate`, reads it
unconditionally. An inheritance bug, not configuration.

**Decision:** mount a `sitecustomize.py` into `kasm_api` that gives the API
classes a falsy class-level `hubspot_api_key`. `if self.hubspot_api_key:` then
evaluates False and the unused HubSpot branch is skipped.

**Alternatives, all tried and reverted** (detail in
`kasm/notes/hubspot-defect.md`): plaintext SQL insert (crash-loops the API —
the column is encrypted), NULL insert (attribute still unset), ORM insert with
correct encryption (row is fine, but `ClientApi.__init__` never runs), and
adding the key to `api.app.config.yaml` (feeds the wrong class). Downgrading to
1.16.x was the other option; 1.17.0 is the only version currently published.

**Consequences:** login works — 518-char JWT issued, authenticated API calls
succeed, invalid credentials still 403. The cost is a runtime patch on vendor
bytecode in the authentication path, which is exactly the kind of clever-over-
boring this project normally rejects. Mitigated by keeping it a mounted file
(remove the mount to revert), failing silently so a bad patch cannot stop Kasm
booting, and documenting it for upstream. **Re-check after every Kasm upgrade.**

## D-017 — The data-root migration did NOT move image storage (containerd)
2026-08-16 · Status: **RESOLVED**

**Context:** O-011 moved Docker's `data-root` to `/mnt/data/docker`
specifically so Kasm's large images would not fill the 48 G root disk. The
`DiskWillFillIn24h` alert fired today and turned out to be **correct**: `/` had
gone from 12 G to 33 G used (68%) while `/mnt/data` sat at 1.1 G.

**Root cause:** Docker 29 uses the containerd image store —
`Storage Driver: overlayfs`, `driver-type: io.containerd.snapshotter.v1`. Image
layers therefore live under **containerd's** root, `/var/lib/containerd`, not
under Docker's `data-root`. Measured:

```
/var/lib/containerd                                  23 G
  io.containerd.snapshotter.v1.overlayfs             17 G
  io.containerd.content.v1.content                  5.9 G
/mnt/data/docker  (Docker metadata only)       953 M
```

The migration moved Docker's bookkeeping and left the bytes behind. The
verification at the time ("data-root is on /dev/sdb1") was true, but it did not
test the thing that mattered — which is why this survived until a real alert
caught it.

**Why it matters:** each Kasm workspace image is 3-4 GB. `Ubuntu Noble` alone
would add ~4 G to a disk with 16 G free. Left alone this ends as a full root
filesystem, which takes down sshd and Docker together.

**Fix (documented, NOT applied):** give containerd its own root on the data
volume — stop `docker`, `docker.socket` and `containerd`; `rsync -aHAX`
`/var/lib/containerd/` to `/mnt/data/containerd/`; write
`/etc/containerd/config.toml` containing `disabled_plugins = ["cri"]` and
`root = "/mnt/data/containerd"`; start `containerd` then `docker`; verify
images and containers; only then reclaim the old directory.

**Why it is not applied:** it stops every container for the duration of a 23 GB
copy. The user declined a reboot minutes earlier, so downtime is theirs to
schedule rather than mine to assume. Not urgent — 16 G free, no active growth
now the pulls are done — but it must happen before more workspace images are
pulled.

**Lesson:** "the setting is applied" is not "the outcome is achieved". The
phase-1 check verified the config, not where the bytes went. A predictive alert
caught what the gate missed, which is a good argument for `predict_linear` over
static thresholds.

### D-017 resolution — applied 2026-08-16

containerd's root moved to `/mnt/data/containerd` via
`/etc/containerd/config.toml` (`root = "/mnt/data/containerd"`), mirrored
in `host/containerd/config.toml`.

Procedure: stopped docker/containerd, `rsync -aHAX` 23 GB (9m39s), wrote the
config, started containerd then docker. Verified BEFORE reclaiming anything —
35 images intact, all 15 containers back with an identical name set, services
serving, 5/5 targets up, and new containers demonstrably runnable from existing
images (the real proof the layers moved, not just the metadata). Only then was
the old directory renamed, re-verified, and removed.

**Result: `/` fell from 68% to 27% (35 G free); the data volume holds 18 G.**

**Second finding along the way:** Kasm's agent **auto-pulls every enabled
workspace image**. That, not our own pulls, is what filled the root disk — 24
kasmweb images totalling 23.9 GB had accumulated. Restricting the catalogue to
Terminal and Ubuntu Noble and removing the other 13 reclaimed ~6 GB. This is
why §29a's "do not install dozens of workspace images" matters operationally
and not just tidily: enabling an image in the catalogue *is* a download
instruction.

## D-018 — Bind publicly; the RDP/SSH target is THIS host, not your-laptop
2026-08-16 · Status: accepted (user direction)

**Context:** `https://100.64.0.10/webrdp` failed with
`ERR_HTTP2_PROTOCOL_ERROR`. Cause: the Tailscale IP matched no `server_name`,
so it hit the catch-all's `return 444` — which closes the connection with no
response, and a browser reports that as a protocol error rather than a
rejection. A 444 catch-all is correct for a named vhost and actively wrong for
a server addressed by raw IP.

The user also corrected O-003: the RDP/SSH target is **this OCI instance**, not
the `your-laptop` laptop.

**Decision:**
1. nginx binds `0.0.0.0:80` and `0.0.0.0:443` instead of the Tailscale IP.
2. The site server becomes `default_server` with `server_name _`, so requests
   addressed by IP are served. The 444 catch-all keeps :80 only.
3. Host firewall opens 80 and 443 (previously deferred to Phase 11).
4. A narrow rule lets Kasm workspaces reach this host's xrdp:
   `172.20.0.0/16 -> 172.20.0.1:3389` only.
5. Remmina enabled as the browser RDP/SSH client. Targets are `172.20.0.1:3389`
   and `172.20.0.1:22` — **not** `localhost`, which inside a workspace means
   the workspace.

**Consequences, stated plainly:**
- Once the OCI NSG allows 443, **this is a public server**. The bind address is
  no longer a control; the NSG and the host firewall are.
- The certificate is still **self-signed**, so browsers will warn. Training
  yourself to click through a warning on a login page is a bad habit to build —
  this should be short-lived, until the domain arrives and certbot can issue.
- Kasm's login page becomes publicly reachable while **MFA is not enforced**.
  Rate limiting (5 r/m on auth) and fail2ban are in place, but MFA is the
  control that matters here.
- Letting a workspace container reach the host's RDP and SSH widens the blast
  radius of a workspace compromise (T4). The rule is scoped to source subnet,
  destination address and single port, but it is a conscious trade.
- Host-based filtering is gone until a real domain exists. Accepting any `Host`
  is correct for an IP-addressed server; restore a proper `server_name` and the
  443 catch-all at Phase 11.

**Regression caught during this work:** relaxing `port-audit.sh` to accept the
new public bind initially wildcarded `0.0.0.0` for dockerd, which silently
whitelisted every dockerd-published port on a public address — blinding the
audit to the exact mistake it exists to catch. Found by the negative control,
which is the argument for having one. Now 80/443 are allowed by port in the
EXPECTED map and nothing is bind-wildcarded.

## D-019 — "No resources available": containers surviving the containerd move had broken overlays
2026-08-16 · Status: resolved

**Symptom:** Kasm refused every session with *"No resources are available to
create the requested Kasm."*

**Diagnosis chain**, each step ruling out the obvious guess:

1. No stale `kasms` rows, no orphaned workspace containers — so it was not
   leftover state from an earlier failed launch (which HAD been the cause once
   before, and was the tempting answer).
2. `servers.operational_status = missing`, `last_reported` ~55 minutes stale.
   Kasm was not short of capacity; it could not see its agent at all.
3. Agent log: `Failed sending heartbeat ... HTTP Error 500`.
4. The 500 came from `kasm_proxy`, and the manager never logged the request —
   so it was failing in nginx, not in application code.
5. `kasm_proxy`'s nginx error log:
   `open() "/var/cache/nginx/client_temp/..." failed (2: No such file or directory)`.
   Small POSTs stay in memory and worked (a `{}` probe correctly returned 401);
   the agent's larger heartbeat buffers to disk and 500'd.
6. Inside `kasm_proxy`: `mkdir -p` returned success while creating nothing,
   `touch /tmp/x` failed with ENOENT, and `mount` listed nothing. The
   container's overlay mount was broken, not merely missing a directory.

**Root cause:** the containerd root migration (D-017). Containers that kept
running across it — and were never recreated afterwards — held stale snapshot
mounts pointing into the old, now-deleted `/var/lib/containerd`. They kept
serving whatever was already in memory or on bind mounts, so they looked
healthy, but their writable layer was gone.

**Fix:** recreate the affected containers so they get fresh snapshots from the
image. `kasm_proxy`, `kasm_manager`, `kasm_agent` and `prometheus` were the
ones still running from before the move; everything else had already been
recreated for other reasons and was fine.

**Verified:** heartbeats succeed, `servers.operational_status = running`, and a
Terminal session created successfully end to end.

**Lesson:** after moving containerd's root, **recreate every container**, do not
just restart the daemon. A container can keep serving traffic with a broken
writable layer, and its healthcheck will happily pass — `kasm_proxy` was
reporting healthy throughout, because its healthcheck only needed to read
config and answer on a socket.

A second lesson about diagnosis: my first probe for this (`touch /tmp/.probe`)
produced false positives on every container running as non-root, and `ls / |
wc -l` produced false positives on images without `ls`. Both briefly suggested
half the stack was broken. The reliable signal was the specific one — the
application's own error log naming the exact failing syscall.

## D-020 — Let's Encrypt via DNS-01, not HTTP-01, and not Cloudflare Origin CA
2026-08-16 · Status: accepted

**Context:** Phase 11 needs a real certificate on the origin. Three options, and
the choice is forced by a constraint that is easy to miss.

**Decision:** certbot with the `dns-cloudflare` plugin, DNS-01 challenge,
wildcard `yourdomain.com` + `*.yourdomain.com`, renewed by
`certbot-renew.timer` twice daily.

**Alternatives:**

- *HTTP-01* — **rejected, and it is not a preference.** Let's Encrypt validates
  HTTP-01 from its own validator IPs. The moment ingress on 80/443 is restricted
  to Cloudflare's 15 published ranges — which is the entire point of putting
  Cloudflare in front — those validators are blocked and every renewal fails.
  The failure would appear ~60 days after the lockdown, long after anyone
  connects the two changes. DNS-01 needs no inbound path at all, which also
  means port 80 never has to be opened.

- *Cloudflare Origin CA certificate* — genuinely tempting: free, valid 15 years,
  zero renewal machinery. Rejected because it is trusted **only by Cloudflare**.
  Grey-clouding any record, or bypassing Cloudflare to debug the origin
  directly, then produces browser errors. A publicly-trusted cert keeps the
  origin independently verifiable, which matters on a box whose direct
  reachability we have already been wrong about twice (see O-020).

**Consequences:**

- Renewal depends on a Cloudflare API token in `/etc/letsencrypt/cloudflare.ini`
  (0600, root). Scoped to `Zone:DNS:Edit` + `Zone:Zone:Read` on one zone. If the
  token is revoked, renewal fails silently — hence `TLSCertMetricMissing`.
- The wildcard means future subdomains need no new issuance. This does **not**
  reverse the path-based routing decision; it is only a convenience.
- The packaged `certbot.timer` is **disabled**. Two renewal timers means
  duplicated ACME traffic and no single source of truth for when renewal runs.
- The deploy hook proves a real TLS handshake after reloading, rather than
  trusting the reload's exit code — consistent with the rest of this platform,
  where "running" has repeatedly failed to mean "serving".

## D-021 — Secret redaction needs a denylist, not just patterns
2026-08-16 · Status: accepted · **Incident**

**Context:** Four live credentials reached `docs/context/audit/*.jsonl`, and the
backup passphrase was **pushed to GitHub** before it was noticed. The hook's
`redact()` was supposed to prevent exactly this.

Two independent failures:

1. The key-name alternation had `passwd|password` but **not `passphrase`**, so
   `BACKUP_PASSPHRASE=...` was written verbatim. It also matched `access_key`
   but not `access_key_id`, because the pattern required `=` immediately after
   the name.
2. More fundamentally: **a secret pasted bare into a command line has no
   `key=value` shape and often no prefix.** An OCI access key is 40 hex
   characters — indistinguishable from a git SHA. No generic pattern can catch
   that without redacting every hash in the log.

**Decision:** keep the pattern rules (widened: `passphrase`, `access_key_id`,
`cfut_`, `glpat-`) **and** add an explicit denylist of active secret *values* at
`/etc/claude-redact.list` (0640 root:prodadmin, never in git). Anything listed is
masked wherever it appears, in any context, matched as a fixed string because
these values contain regex metacharacters.

**Alternatives:**
- *Pattern matching alone* — demonstrably insufficient; that is this incident.
- *Entropy-based detection* — would flag every container ID, image digest and
  commit SHA. Unusable in a log that is mostly those.
- *Never log command text* — throws away the audit trail's main value.

**Consequences:**

- A new secret must be added to the denylist **when it is created**, and removed
  once rotated. A denylist of dead secrets is just a file of secrets.
- The denylist is itself sensitive and lives outside the repo, which means it is
  one more thing that must be recreated on a rebuild. It is included in the
  off-site backup's `/etc` tar.
- **Scrubbing does not undo the leak.** Per rule 30 all four values must be
  rotated; the passphrase is already in GitHub history where removing it from
  the working tree changes nothing. Rotation is the fix; redaction only stops
  the next one.
